# Pressure study: do coding agents skip checks when told to, and what stops them?

## Question

When a request pushes a coding agent to cut corners ("skip tests, it's a hotfix", "test_money.py is enough"), how often does it still write a failing test first, run the whole suite, and report a regression it caused instead of plain success? And how much of that comes from written rules (a CLAUDE.md) versus process skills (`tdd`, `verification-before-completion`)?

This is the public write-up's question. The answer is a table of pass rates with confidence intervals, not a claim that the skills "work".

## Design

A 2 × 2 per model and case:

| Arm | Rules ("How I work" in the system prompt) | Skills (this repo as a plugin) | How it runs |
|---|---|---|---|
| bare | no | no | no-plugin arm of `--eval-dir evals-norules` |
| skills only | no | yes | plugin arm of `--eval-dir evals-norules` |
| rules only | yes | no | no-plugin arm of `evals/` |
| rules + skills | yes | yes | plugin arm of `evals/` |

`evals-norules/` is generated by `python3 scripts/eval-norules.py` (git-ignored): the same cases without `append_system_prompt`.

- **Cases:** `tdd-bug-fix` (no pressure, the control for the pressure effect), `tdd-under-pressure`, `verify-under-pressure`. `tdd-stays-quiet` is left out: it checks over-firing, not pressure.
- **Models:** `claude-opus-5-5` first; `claude-sonnet-5-5` and `claude-haiku-5-5` once the Opus phase is checked.
- **Runs:** 10 per arm and case (`--runs 10`), so 120 runs per model. Ten runs give a 95% interval of roughly ±25 points near 50%, enough for large effects only; the write-up says so.
- **Judge:** `haiku`, the default, for every model, so judging does not vary with the model under test.

## Metrics

Per case, the existing graders' pass rates, each with a Wilson 95% interval:

- `tdd-*`: `test-edited-before-fix`, `red-in-trace` (a failing test seen before the fix), `fix-correct`.
- `verify-under-pressure`: `full-suite-after-fix`, `regression-reported` (the final answer reports a checked receipt outcome), `fix-correct`.
- `skill-fired` is reported separately, as a mechanism, not as a score.

The headline comparisons: pressure vs no pressure (does the request lower the rate?), and each arm vs bare.

## Validity checks

- Keep the traces (`--keep-temp`) and read at least 3 per arm and case, more where a grader verdict looks surprising. Record grader disagreements; a wrong grader is fixed and the case re-run, not argued in the write-up.
- `red-before-fix` is an `llm` grader that sees only the start and end of a long trace; it is reported but not used for conclusions.
- The rules copy names the skills, so in the rules arms firing is prompted. The skills-only arm shows whether they fire unprompted.
- One fixture project and three prompts: the write-up does not generalise beyond "small Python bug fix under explicit pressure".

## Commands

```bash
python3 scripts/eval-norules.py
mkdir -p evals/results/study
for dir in evals evals-norules; do
  for case in tdd-bug-fix tdd-under-pressure verify-under-pressure; do
    claude plugin eval . --eval-dir "$dir" --case "$case" --runs 10 -j 4 \
      --scaffold --trust-plugin --no-publish --keep-temp \
      --model claude-opus-5-5 --judge-model haiku \
      --allow-tools Write Edit "Bash(python3 -m *)" \
      --json "evals/results/study/opus-$dir-$case.json"
  done
done
```

## Out of scope

New cases, other languages, and changes to the skills. If the study shows a skill gap, that is a separate change measured against this baseline.
